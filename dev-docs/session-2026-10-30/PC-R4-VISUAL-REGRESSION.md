# PC R4：恢复视觉修复的启动契约

用户在 R3（`8F7932FB`）空档开场重新看到 CG 甲板扫描线，入局后部分材质边沿也出现条纹。当前 MSAA 为 0。不能用此前菜单/字幕截图或高 FPS 代替这项视觉验收。

## 查到的缺口

- Windows GLES1-on-GL2 的 `RenderbufferStorageOES` 原样分配游戏请求的 D16；SDL 窗口配置 D24 不会升级游戏自己的 FBO。EAGL 的 MSAA 路径另外分配 D24，因此旧 PC MSAA 基线掩盖了关闭 AA 后的深度依赖。
- Android native GLES1 已有相应 D16→D24 修复，桌面后端此前没有。R4 增加限定于有效 D16 renderbuffer、由 `TOUCHHLE_DS_PC_DEPTH24=1` 控制的桌面修复，并记录实际分配位数；用户的 MSAA 选择不变。
- PC 启动器、辅助 PowerShell 和 quiet runner 原先分别提供部分视觉选项。内容 key 限定的额外 alpha mip 表只在 Android 默认项中；不能靠旧宿主进程的残留环境继承。
- 雾过渡和血迹开关在渲染器中缺省为启用；R3 没有显式环境值，不能据此断言这些代码被关闭。R4 将默认值显式写入共享配置以供审计。

## 防止再次遗漏

`tools/pc-runtime/DeadSpace-VisualCompat.ini` 是 PC 启动器和 quiet runner 共用的视觉基线。启动器将它嵌入 EXE，每次启动游戏先应用基线，再应用用户的画质、同步、mip 等选项。直接打开新复制的启动器也能继承修复，无需从某个旧 PowerShell 窗口启动。

`VisualCompatibility.cs` 在创建游戏进程前写出 `DeadSpace-visual-effective.ini`，包含实际子进程的深度、MSAA、修复 key、纹理同步和 EXE SHA-256。`<unset>` 与 `0` 明确区分。

关键依赖注释同时位于桌面深度分配函数、启动器采样设置附近和共享配置头部。不要通过强开 MSAA、跳过船体/甲板几何或删除纹理掩盖回归。

编译后配置测试验证：空宿主环境与冲突宿主环境两种情形、EXE 内嵌的 19 项配置、以及 MSAA=0 时 D24 修复仍启用。此配置测试不代替实际 GL 分配和完整运镜检查。

## 回归方法与存档

用同一候选 EXE、同样的 GPU 和输出/倍率，在 MSAA=0 下分别设置 D16 与 D24，记录实际深度位数并抓取同一段 CG 的内部截图。视觉对照按相同机位/运镜位置比较；不从不同进程的冷启动 FPS 推断性能收益。

R3 的用户新档和运行目录保留。R4 使用独立副本，本轮先使用活动 `00_*` 空档复测。后续奖励房与商店测试由代理备份后直接切换活动 `00_*` 文件；仅把其他档放到 `01_*`/`02_*` 不代表用户当前入口可以切换到它们，也不要求用户使用尚无一键导入的编辑器。

## R8 源码归档与最终启动配置检查（2026-10-31）

D24 桌面分配补丁、五项 alpha mip 的常驻注释、共享配置、启动器内嵌与构建检查已从脏工作树单独提取。独立源码目录通过 100 项 DS Rust 测试，0 失败；所编译的两个 Rust 文件与候选索引一致。此处仅增加防遗漏和归档，不替换当前 R7i 真人测试二进制。

`VisualCompatibility.WriteEffective` 在最终子进程环境处检查 D24 和两个 mip 表中的五个必需 key，防止后续预设覆盖已应用的基线。11 个覆盖/删 key 反例必须拒绝；额外纹理 key 仍允许。构建测试同时验证空/冲突父环境、19 项内嵌默认值、MSAA=0、PC/Android 表一致性，并单独保留显式深度 hash 诊断。隔离反例版本只移除最终检查调用，测试即失败，证明此检查实际参与防回退。

构建脚本也固定用户已验收的旧样式退出框：清除已知内容为 `1` 的实验标记，不自动重新生成它；遇到目录、链接或内容不明的同名项则停止，保留文件。`Test-LauncherQuitDefault.ps1 -OutputDirectory <private-output>` 验证旧标记清理、未知标记和既有输出保留，不运行启动器或游戏。
