## 工具与用法（⚠ 先看这里，别踩）

二进制：`device-app/extracted/Dead Space.app/Dead Space`（Mach-O ARM，**符号表完好**，含 C++ 修饰名）。

| 工具 | 用法 |
|---|---|
| `tools\syms.py [pattern]` | 按子串列符号（如 `Door` / `Interact` / `Hud`），输出 `地址 修饰名` |
| `tools\arm-dis.py <bin> <符号子串\|@VA> <arm\|thumb> <条数>` | 反汇编某个符号 |
| `tools\arm-scanrefs.py` / `arm-strref.py` | 搜代码里对某地址/字符串的引用 |
| `tools\arm-findcalls.py` | **找 `bl` 调用点**：`arm-findcalls.py <bin> <目标VA>` ⇒ "谁调用了这个函数"（本次定位交互环调用者的关键工具） |
| `tools\arm-findoffset.py` | **按结构偏移找字段访问**：`arm-findoffset.py <bin> <0x1d0>` ⇒ 列出所有 `ldr/str rX,[rY,#off]` 读写点（自动跳过栈帧/分支/常量；⚠ 需 `skipdata=True`，否则 `__TEXT` 开头非代码会一条都解不出） |
| `tools\mach-dump.py` | 段/偏移换算（符号 VA → 文件偏移） |

⚠ **ARM/Thumb 判定**：Mach-O 里**符号地址偶数 = ARM，奇数 = Thumb**。
本作这些 C++ 函数**都是 ARM**（例如 `0x00115e88`）。用错模式会得到"看着像指令、其实是垃圾"的结果
（第一轮我就踩了：Thumb 模式反汇编出来全是 `lsls/b` 乱码）。

## 已定案条目

### ✅🎯 D-001 `GameObjectDoor::IsOpen()`：门开合 = `this+0x1d0 ∈ {4,5,6}`

```
0x00115e88  __ZNK14GameObjectDoor6IsOpenEv
  0x00115e88  ldr   r0, [r0, #0x1d0]     ; r0 = *(u32*)(this + 0x1d0)   状态字
  0x00115e8c  sub   r1, r0, #4
  0x00115e90  mov   r0, #0
  0x00115e94  cmp   r1, #3
  0x00115e98  movlo r0, #1               ; return (state-4 < 3)  ⇒ state ∈ {4,5,6} 时为"开"
  0x00115e9c  bx    lr
```

**含义**：门的状态是对象内**偏移 `0x1d0` 的 32 位字段**；状态 4/5/6 = 开（其余=关）。

**用途（这是本轮反编译的最大收获）**：
1. 用 `TOUCHHLE_DS_SCAN_VTABLE`（扫 `__ZTV14GameObjectDoor + 8`，ARM EABI 里对象里存的是 vptr+8）
   找到门口的 `GameObjectDoor` 实例地址；
2. 读 `实例+0x1d0` 的 32 位值：**E 之前应为"非 4/5/6"，E 之后若变成 4/5/6 ⇒ 门确实开了**。
⇒ **与镜头无关、与画面无关的验收判据**，直接解决本冲刺"按 E 能开门"无法判定的问题。

### ⚠❌ D-003 更正（2026-10-11 11:30）—— **对照实验否定了"E 触发状态变化"的归因**

### 🎯🔍 D-004（2026-10-11 13:05）**交互环的绘制判定找到了：`this+0x164` 字节标志 + `this+0x19c` float 门槛**

先用新工具 `tools\arm-findcalls.py`（扫 `bl` 目标）找 `Hud::RenderHUDInteractO2`（`0x18b618`）的调用者：

```
000d5838  bl -> 0018b618   GameObjectInteractive::RenderHUDInteractions(im::SpriteGraphics&)
```
⇒ **只有基类 `GameObjectInteractive::RenderHUDInteractions`（`0x000d5644`）画这个环**；
门的同名覆盖（`0x00115e84`）是空 stub（D-002）⇒ **门不自己画，由基类统一画**。

再反汇编基类该函数，判定条件是：

```
000d565c  add   r0, r5, #0x19c        ; this+0x19c（float）
000d5664  bl    #0x5d660              ; getter → s16
000d5678  ble   #0xd587c              ; ★ s16 ≤ 阈值 ⇒ 直接 return（不画）
...
000d56e4  blx   r6                    ; 虚调用 vtable+0x58 → 返回码
000d56ec  bne   #0xd5728              ; 非 0 ⇒ 另一条路径
000d56f4  cmp   r6, #0x13             ; (类型)
000d56fc  ldrb  r6, [r5, #0x164]      ; ★ this+0x164 字节标志
000d5704  beq   #0xd5860              ; ★ = 0 ⇒ 不画环
000d5720  bl    #0x18b850             ; ★ 画
```

**含义（可直接做探针）**：

| 字段 | 类型 | 作用（推断） |
|---|---|---|
| `this+0x19c` | float | "是否够近/够显著"的门槛（≤ 某常量就不画） |
| `this+0x164` | **byte** | ★ **"当前可交互/被选中"标志**：非 0 才画环 |

**下一步实测**：把跟踪器指向 **`+0x164`**（`TRACK_OFFSET=0x164`、`TRACK_LEN=1`、`TRACK_ALL=1`；
vtable 用 `0x00a7c5c8`（`__ZTV21GameObjectInteractive+8`）**加上**门的 `0x00a7d7b8`），
看走到门口/按 E（或帧脚本点圈内）时有没有任何交互对象把这个字节置 1：
* **有** ⇒ 游戏认为"可交互"，那 E 不生效就是点/时序问题；
* **没有** ⇒ **游戏从不认为玩家能交互**（同时解释了环和环内文字为何都没画），根因往上游查
  （玩家位置/朝向/物理，或被我们改过的投影/视口/`stick-to-touch`）。

### ★★★✅ D-033（2026-10-11 收尾轮十六）**念力（F）不需要举枪 ⇒ 它就是物体上的 `0x10` 提示；F 已接入同一机制**

需要瞄准态采样或新思路；念力既然不是其一，就不再受"进不了瞄准态"阻塞。

000e5664  cmp   r2, r3 / bne 返回
000e566c  mvn   r4, #0x3e8          ; ⇒ 类型 -1001

001171d4  str   r1, [r0, #0x1d0]      ; 写新状态
001171d8  cmp   r1, #8
001171dc  str   r2, [r0, #0x1d4]      ; ★ 清 +0x1d4
001171e0  strb  r2, [r0, #0x164]      ; ★ 清"可交互"标志（D-004 那个字节）

001171f8  add   pc, r0, r2

### ✅🔍 D-035（2026-10-16）**补齐 D-034 里两个"未定名"码：`0x07` / `0x08` 的行为**

目标项⑧。仍**没有**按钮名（`InputSchemeBasic` 的 5 个按钮名与码的对应没钉死），但**行为已经读全**：

**`0x07`（跳表目标 `0x543c8`）——"瞄准态下的 HUD/音效动作"**

守卫（顺序即代码顺序，任一不满足直接跳到 `0x54a88` 返回）：

```asm
000543d0  tst  r4, #4          ; [player+0x1a4] bit2 必须为 0
000543e0  cmp  r4, #5 / bhi    ; sel = [player+0x2ec] <= 5
000543f0  ldr  r4, [r4, #0x2d4]        ; ★ 选中武器（weapon slot sel）
000543fc  ldrb r5, [r4, #0x164]        ; ★ 该武器自身的"可用/选中"字节必须非 0
0005440c  ldrb r5, [r6, #0x1e1]        ; ★★ 必须是瞄准态（SetAiming 写的那个字节）
0005441c  cmp  r5, #0 / bne            ; state = [player+0x208] 必须 == 0（空闲）
0005442c  ldr  r4, [r4, #0x28] / cmp #0x37   ; 按武器类型分两条路
…
000544cc  bl   #0x302edc               ; SoundManager::PlaySound(名字, 位置)
…                                      ; 之后还有 m3g::Appearance::SetUVOffsets
```

⇒ **它要"瞄准中 + 空闲 + 选中武器可用"**，效果是**播声音 + 改 m3g 外观的 UV/合成模式（HUD/特效动画）**，
**不调用 `OnTryFire`** ⇒ 不是开火，更像"瞄准态下的某个 HUD 动作"（换模式/扫描/手电之类）。
**这条也解释了用户问的"不瞄准也能发静滞"**：静滞是 `0x0b`，它**没有**瞄准守卫；而 `0x07` 这类动作**才**要求瞄准。

**`0x08`（跳表目标 `0x545ac`）——"中断/取消当前武器动作（Abort 路径）"**

```asm
000545b4  tst  r4, #1          ; [player+0x1a4] bit0
000545c4  (state<=0x1f 且 state 命中位掩码 0xee03ef06) -> 直接返回
000545e4  tst  r4, #0x40
000545ec  cmp  state,#3 / cmp #5 / cmp #6   ; 三条分支
0005461c  r0 = [player+0x2d4 + sel*4]        ; 选中武器
00054634  ldr  r5, [r5, #0x188] / blx r5     ; ★ vtable+0x188 = Weapon::OnAbort
00054640  r0 = [player+0x30c]                ; 当前装置（实测 = WeaponStasis）
00054658  ldr  r4, [r4, #0x188] / blx r4     ; 也是 OnAbort（state==5 时）
0005469c  bl   #0x485c8                      ; StateTransition(0) —— 回空闲
```

⇒ **`0x08` 的实质是"Abort"**：对**选中的武器**或**当前装置**调 `OnAbort()`（槽 98 / `+0x188`），
随后按返回值把玩家 `StateTransition(0)`（回空闲）。它对应的转发器监听的是 **`0x3ec`（1004）**而不是单击 `0x3e9`，
所以它不是"点一下"（更像另一种指针事件）。

**⚠ 一条要带下去的教训**：`InputSchemeBasic` 提供了
`SetAltFirePos / SetReloadPos / SetStasisPos / SetSlashEnable / SetStompEnable` 五个按钮配置，
但**走廊里玩家实际持有的 5 个码是 `{0x06,0x07,0x08,0x0a,0x0b}`**，而 `0x0d`（Stomp）/`0x0e`（Slash）
当时**根本没有启用的转发器** ⇒ **不要用"按钮名"去反推码**；以跳表（码的行为）为准。

#### ⚠⚠ 同日更正：**`0x09` 不是"举枪"，是"放下武器/取消瞄准"**

把 `0x09` 的跳表目标（`0x000546fc`）逐条读完后发现：

VM 实测也支持这一点：`TOUCHHLE_DS_SEND_ACTION=0x09` 在各场景都报 `no enabled forwarder`；
用输入工具的 `dn`（按住）、`dn`+`mv`（按住后拖动）分别试了中心/视角锚点，
`[DSgauge] aiming` **全程 0**（`vm\_holdaim*.ps1`）——具体是哪种手势仍待用户确认。

### D-039 🎯✅📄 QTE 可以完全绕过触摸事件

`GameObjectPlayable::RenderGrapple` (`0x4001c`) 同时揭示了实际输入入口：

* Tap（`+0x37c == 5`）：
  `OnGrappleEvent` (`0x41014`) 的 `PointerEvent<1001>` 分支读取
  `[player+0x384] -> vtable+0x34` 选择 tap slot，再从全局
  `0x7e448()+0xbb8/0xbbc` 取内部事件值写入 `player+0x3ec`。
* Swipe（`+0x37c == 1/7`）：
  `OnGrappleGestureEvent` (`0x40cb8`) 只读取事件对象的
  `+0xc/+0x10`（起点）和 `+0x14/+0x18`（终点），计算角度；状态 1 接受
  `12..78°`，状态 7 接受 `-123..-57°`。

✅ `dd19b308` 已按此实现：

* tap 直接复刻 vtable+slot→`+0x3ec` 写入；
* swipe 在 guest 内存构造 0x1c 字节 `GestureEvent` 后直接调用 `0x40cb8`。

因此 QTE 不需要 SDL 触摸、屏幕坐标或 `tap/swipe` 队列；键盘/手柄只需触发 E。

### D-040 🎯✅ QTE state 7 的安全方向向量

`OnGrappleGestureEvent` 对 `player+0x37c == 7` 的角度守卫是 `-123..-57°`。原先构造的
`(100,0)->(0,0)` 是 180°，永远不满足该守卫；已改为：

`src/frameworks/opengles/gles_guest.rs::ds_try_current_prompt_gesture`。

### D-041 🎯✅ EAGL guest viewFramebuffer 与 MSAA attachment 顺序

运行时 FBO 日志证明 Dead Space 的标准 EAGL 初始化路径不是“直接绘制 guest framebuffer 0”：

```text
guest bind framebuffer 3
attach depth RB 4
attach drawable color RB 1
guest bind framebuffer 0 -> host MSAA framebuffer 2
guest bind framebuffer 3 (real render target)
```

因此只把 guest framebuffer 0 重定向到 MSAA 不会生效；而只替换 drawable color、不替换 depth
会产生 `COLOR=4x / DEPTH=1x` 的 mixed-sample FBO，FBO 不完整，所有 draw 被丢弃并得到黑帧。

✅ 实现规则（`src/frameworks/opengles/gles_guest.rs::glFramebufferRenderbufferOES`）：

1. guest 把 `renderbuffer_drawable_bindings` 中的 drawable color 附到任意 FBO 时，替换为
   `msaa_color_renderbuffer`；
2. 同时补挂匹配的 `msaa_depth_renderbuffer`；
3. 后续 depth attachment 若检测到当前 FBO 的 color 已是 MSAA color，也替换为 MSAA depth。

VM llvmpipe 结果：requested 4/8/16 → actual 4/8/8（16 被 `GL_MAX_SAMPLES_EXT` 钳制），
最终 backbuffer 不再全黑；组合 MSAA8 + FSR1 的 1920×1280 截图 non-black=99.10%。
